Context and data boundary

Initial scope: submitted material and required versioned reference standards. Explicit caller-supplied context is an extension through a defined contract. Entity/state calls are not part of the initial extraction pipeline.

Information neededBoundary and treatment
Source documentsGoverned retrieval by reference; source identity, location and content hash.
Reference standards / supplied contextNamed owner, version or snapshot, authorisation and freshness; distinguish context from document assertions.
Future bounded lookupA demonstrated need and explicit architecture decision; typed read-only contract, timeout and unknown/hold disposition.
Live trade / payment stateConsuming application owns reconciliation, eligibility, workflow and actions.

Define governed data products and access patterns per use case. Unity Catalog, analytical/query federation and application APIs serve different purposes. No additional business-data pool or RAG dependency is assumed for the initial baseline. Azure Databricks federation documentation

Use-case assumptions and central reuse

The selector illustrates proposed profiles, not benchmarked routes. Trade inputs are described as mailbox-based; SSI uses the application/FileNet path; legal documents use an authorised SharePoint location. Access and integration ownership need service-owner confirmation.

Model, vision and IDP/parser routes are chosen on measured fit. Embeddings, vector retrieval, agent templates and traditional MLOps remain available patterns for other workloads; they are not dependencies merely because they appear in the wider AI Factory catalogue.

Generic extraction, validation or evaluation mechanisms can be centrally supplied. SIFT maintains the Markets contracts and integrations where needed; domain owners retain semantic acceptance wherever the machinery runs.

Delivery capacity

Scale through domain contributions, package templates, automated checks and clear maintenance ownership. The shared team should not need to author every use-case change.

Runtime capacity

Scale with measured concurrency, quotas, queues, isolation and dedicated capacity where required. Additional instances do not remove shared model or gateway limits.

Placement decision framework

First: confirm SIFT scope, separate the surrounding business workflow, apply data/access and service constraints, and name a funded operator. Then choose the least costly viable placement.

FactorShared execution favouredReason to consider another placement
Reuse and specificityDifferences fit schemas, prompts and package configuration.Specialised runtime code repeatedly conflicts with the common implementation. A unique schema alone is insufficient.
Access and live-data interactionAuthorised inputs and explicit context satisfy interpretation needs.Proven locality or access constraints; first check whether the live-state work belongs outside SIFT.
Tenancy and resilienceLogical isolation and shared resource controls meet requirements.Dedicated resources or stronger fault boundaries are required; the shared team may still operate them.
Volume and latencyMeasured demand fits available runtime and model capacity.Another placement materially improves tested requirements; include downstream quotas and network cost.
Delivery and ownershipPackage contributions can progress within shared compatibility rules.Sustained lifecycle independence with named maintainers, support and full operating-cost ownership.

Record the rationale, operator, package owner, conformance evidence and review trigger. A new deployment is not the default answer to a delivery backlog.

Runtime modularity and portability

Spring Modulith is a candidate implementation approach. It supports logical modularity within Spring Boot, not automatic independent deployment, scaling or fault isolation. Configuration packages can activate independently only where the runtime supports it; compiled extensions may require a new runtime release. Spring documentation

Initial portability target: move a package between approved instances of the supported runtime, retaining its identities, contracts, evidence and evaluation behaviour. Demonstrate one package on a second deployment before claiming portability is proven.

Version interfaces and deployment bindings; plan in-flight work, access and evidence migration. Stochastic model outputs require quality comparison rather than a promise of byte-identical replay. Dedicated deployments introduce additional operating cost and drift management. Azure deployment-stamp guidance

Service acceptance exercise and artifact authorities

Demonstrate one complete use case

  1. Change a prompt or model and pin the candidate package.
  2. Evaluate a governed corpus; inspect a critical-field regression.
  3. Approve and deploy the selected package.
  4. Trace a result back to its source and actual model invocation.
  5. Record a domain correction and correlate the later business outcome.
  6. Compare iteration effort, controls, delivery commitment and full operating cost.

Keep clear authorities

One designated authority for each artifact class within its agreed scope: prompt versions, approved corpus, package/release record and scoring policy. Domain use cases retain their own semantics and acceptance criteria.

Telemetry export does not synchronise prompts, datasets, scores or approvals. Additional copies need a purpose and a data/retention policy. Azure / Langfuse trace integration

Business review remains in domain applications; evaluation annotation is a separate workflow.

Confirm in order: vendor capability → internally enabled service → supported operation → demonstrated SIFT fit. Availability, operator, access, retention/export, costs and delivery dates require service-owner evidence.
